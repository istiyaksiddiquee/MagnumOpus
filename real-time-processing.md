# Real-Time Data Processing Architecture of Magnum Opus

![real-time-processing](real-time_stream_processing_pipeline.jpg)

A streaming data processing pipeline processes the data in real-time, that is, as soon as the data arrives it will be able to process or summarize the data. This is the difference between traditional batch processing and stream-processing: in batch processing, the system waits until the data forms a little batch, but in stream-processing there is not waiting. Apache Kafka is a phenomenal choice for batch processing but it does not possess the capabilities to process the data in real-time. As a result, we need a special kind of data processor. For this purposes, Apache came up with Flink. This tool can process the data in real-time stream mode. It has a working memory that enables the processor to perform tasks like moving average, streaming k-means clustering, etc.

In this pipeline, I have utilized and demonstrated how this can be done. In addition, I have also used Apache Pulsar, instead of Apache Kafka. Although Kafka is a widely adopted technology, it has some serious design issues which can even create a single-point of failure for a otherwise resilient architecture. So it is wise to move away from Kafka gradually and select a tool that has already handled the issues Kafka faces. To remediate this, Apache brought Apache Pulsar. This tool has so many update that I believe if someone wants to truly understand fail-safe distributed cloud-native architecture they should consider studying the design choices made by the Pulsar team.

In this pipeline, I start by producing the NYC TLC dataset to Pulsar via Python. Ideally, this data should not be read from a stale text file, rather we should stream the data directly from the gold layer of the lakehouse. But unfortunately I do not possess enough compute resources to keep everything afloat in one computer. As a result, I am choosing to stream the data from text based format. This data is sent to Apache Pulsar. From Pulsar, a subscription is maintained by Apache Flink. As soon as the data arrives in the designated partition (Paritition 1), the data is processed by Flink and the result is fed to a separate partition (Partition 2). This partition is being subscribed by Apache Pinot. Pinot is a great choice for OLAP database that works nicely with Pulsar. So we can directly get the result of the stream processor from Pulsar. Then this result is immediately visualized by Apache Superset which is another great tool to visualize data properties, often in real-time. So Superset maintains a web-socket connection with Pinot, which allows Superset to instantly visualize the outcome read by Pinot from Pulsar, which was produced by Flink.

This architecture has many different benefits.
